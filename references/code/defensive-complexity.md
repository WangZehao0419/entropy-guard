# 编码：防御性复杂度

适用：写新代码、改代码、代码评审时，判断「这个防护该不该加」。

核心原则：复杂度按真实故障概率分配。十行需求配百行防御，成本没有消失，只是从写代码的人转移给了所有读代码的人。

## 八条规则

1. **不为假想故障加复杂度**：不要为猜测出来、几乎不会发生的竞态或安全边界情况增加处理逻辑。
2. **要加先报账**：确实认为需要加，先说清三件事——具体会怎么出错、发生概率多大、要多写多少代码。得到同意再动手，不悄悄扩大改动范围。
3. **入口校验一次**：外部传进来的数据，只在入口那一层校验。往里传已经确定类型的值，内部不再重复做防御性检查。
4. **不提前抽函数**：只用一次的逻辑不要先抽出来。只有会复用、包住了确实复杂的逻辑，或者它代表一个能起清楚名字的概念时才抽。
5. **主函数只写正常流程**：校验与细节放到它下面的小函数里，主函数读起来是一条直线。
6. **注释只写不明显的**：写约束和反直觉的行为，不给显而易见的代码写注释。
7. **生成文件不手改**：自动生成的文件改源头后重新生成。
8. **按仓库现有流程走**：测试测真实实现，不把业务逻辑抄一份进测试，尽量少用 mock；不引入仓库没在用的工具或流程。

## 判断顺序

1. 这个防护针对的故障，实际出现过吗？没出现过且概率低，不加。
2. 必须加时加在哪一层？只加在数据入口。
3. 要写多少行？新增防护超过被保护逻辑本身的量级时，重新评估。
4. 用户没提、仓库也没先例？默认不加，先问。

## 交付前自检

- 每处新增防护都能追溯到具体故障、明确要求或既有约定，而不是「万一」。
- 类型校验只出现在入口，内部没有重复检查。
- 新增函数至少满足其一：会被复用、封装了确实复杂的逻辑、代表一个能起清楚名字的概念。
- 注释解释的是约束与反直觉点，没有复述语句。
- 没有手改生成文件，没有引入仓库未使用的工具或流程。
- 测试针对真实实现，mock 的使用有明确理由。
