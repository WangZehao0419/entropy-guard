# 编码：减熵规则

适用：写代码、改代码、重构、代码审查、脚本与配置优化。

核心原则：易读、易懂、易维护。优先考虑可读性，而不是追求代码简短。

## 十条规则

1. **减少封装**：不要过度拆分函数，不要为了复用而抽取大量辅助函数。只有职责独立、确实有复用价值的逻辑才单独封装。
2. **减少修饰和包装**：避免不必要的装饰器、类、继承、静态方法、属性包装和上下文管理器。只保留确实有必要的设计。
3. **减少嵌套**：优先使用提前返回（Early Return），减少多层 if、try 和 with 嵌套，让主要执行逻辑尽量保持扁平。
4. **优先使用直观语法**：多使用普通的 if/else、for、try/except/finally，少使用复杂的推导式、三元表达式、隐式技巧和过于简洁的语法。
5. **避免过度压缩代码**：宁可多写几行，也要把执行步骤和逻辑关系表达清楚。不要为了减少代码行数牺牲可读性。
6. **注释使用中文**：所有注释和 Docstring 使用简洁、准确的中文。注释重点解释代码的目的、设计原因和关键逻辑，不要简单重复代码本身。
7. **命名清晰**：变量、函数和类的名称应尽量直观，让读者不需要反复跳转就能理解其作用。
8. **保持原有功能**：优化代码结构时，不随意删减功能、改变业务逻辑、修改接口或改变异常处理语义。
9. **谨慎处理复杂机制**：涉及异步执行、上下文传播、异常处理、资源释放、并发和数据安全时，优先保证正确性，不为简化代码而破坏原有行为。
10. **控制优化范围**：不引入不必要的第三方依赖，不为形式上的架构整洁增加抽象层。

## 输出要求

- 先给出完整的优化后代码，不要只给局部片段。
- 代码中的注释和 Docstring 全部使用中文。
- 再简要说明主要修改点及修改原因。
- 对可能影响原有功能或存在兼容性风险的修改，单独指出。
- 不要为了展示设计模式而增加不必要的复杂度。

## 最终目标

让一个刚接触该项目的开发者，也能按照代码从上到下的顺序，理解每一步在做什么、为什么这样做。

## 易踩的四条边界

1. **异常语义**：合并 except 分支、放宽捕获范围、把异常改成返回值，都属于改变行为。要么不动，要么在交付里单列风险。
2. **资源释放**：删掉 with 只为了少一层缩进会漏释放文件、锁和连接；提前返回要在返回前完成清理。
3. **异步与上下文**：去掉 await、改写上下文管理器、把并发逻辑串行化，会改变执行顺序与上下文传播，属于高风险改动。
4. **公共接口**：重构私有实现可以自由调整，公共函数签名、返回结构、错误码一旦变化必须显式声明。

## 交付前自检

- 交付的是完整文件或完整函数，不是省略号片段。
- 注释与 Docstring 全中文，解释目的与原因，不复述语句本身。
- 修改点清单与代码一一对应，风险项已单列。
- 没有为风格改动引入新依赖或新抽象层。
- 原有功能、接口、异常语义未被改变；如已改变，已显式声明。
